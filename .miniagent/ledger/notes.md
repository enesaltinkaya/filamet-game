## brainstorm

## Core difficulty

The Filament surface is small and bounded (~6 source files + 2 CMakeLists), so the real difficulty is not code volume: it is (a) an asset-format gap that must be closed *before* the new renderer can be validated at all — gltfpack's meshopt string compression (`-kn -kv -ke` in `scripts/build-terrain.py:533`) which Diligent's cgltf-backed GLTFLoader cannot decode, plus KTX2/UASTC textures which Diligent's TextureLoader cannot decode — and (b) a semantic remap from Filament's entity-centric scene (per-entity materials, `scene.addEntities`, `IndirectLight`, `MaterialInstance` overrides) onto Diligent's buffer-centric pipeline (GLTF_PBR_Renderer scene, custom SRB bindings, ambient light via the IBL slot) while keeping the three public contracts intact: `gltfEntitiesNamed`, bounding-box camera framing, and animation tick.

## Reductions / key lemmas

1. **Boundary invariant**: everything outside `c-engine/renderer/*`, `c-engine/gltf/*`, `c-engine/terrain/*`, `c-engine/gui/*`, `c-engine/pch.h`, `c-engine/ecs/system/flyingCamera/*`, `c-game/game/Game.cpp`, `c-game/game/mainMenu|credits/*`, `scripts/build-terrain.py` (gltfpack flags + manifest `material` field) and the two CMakeLists is untouched (ECS, paks, input, datamanager, windowing, `ktx2bc7` baking pipeline). Every phase is independently gated by `./scripts/build.sh` + `ENGINE_SCREENSHOT`.
2. **Asset-first ordering (one-way door, cheap to check)**: the re-exported GLB must be loadable by the *Diligent* loader path before any renderer code is written — and, because the re-export changes a checked-in asset, it must also still work in the *current* Filament/gltfio build (plain-string node names decode fine in gltfio, so this is expected to pass). Cheap two-sided validation in Phase 0 makes the entire GLB re-export reversible.
3. **GUI stub is required inside Phase 1, not Phase 4**: `GuiManager.cpp` currently uses `filagui::ImGuiHelper` and `c-game/CMakeLists.txt` links `libfilagui.a` — both need a filament `Engine*`. A Diligent-only Phase 1 therefore cannot build while `gui::guiIsActive()` drives a filament view. Phase 1 must replace the ImGuiHelper with a no-op (or minimal `imgui_impl_vulkan` behind the existing gate) so the window/clear-color acceptance is honest; the full menu returns in Phase 4.
4. **Terrain risk is decoupled from texture assembly**: the KTX2→BC7 2D-array byte assembly in `Terrain.cpp` (parallel `loadLayer` jobs, KTX2 container parsing, basisu UASTC fallback) is engine-agnostic and ports nearly as-is; only the final upload (BC7 blocks → Diligent `ITexture`) and the material binding change. Phase 3's real risk is the splat shader + SRB, not the 492-line file.
5. **ImGui single-copy rule**: the game's thirdparty imgui is 1.92.6 (`IMGUI_VERSION "1.92.6 WIP"`) with prebuilt `imgui/git/build-{linux,win}/libimgui.a`; `backends/imgui_impl_vulkan.cpp` ships in `imgui/git/backends/` and must be compiled into c-engine against that lib. `libDiligent-Imgui.a` (bundles 1.85) must never be linked; if a DiligentFX object drags in imgui symbols, rebuild that one target with `DILIGENT_DEAR_IMGUI_PATH` pointed at the game's imgui.
6. **Link surface is small**: prebuilts expose umbrella libs — `DiligentCore/libDiligentCore.a`, `DiligentFX/libDiligentFX.a`, `DiligentTools/libDiligentTools.a`, `DiligentFX/Radient/libRadient.a` (linux in `git/build-linux`, win32 in `git/build-win`), with headers in the source-tree `*/interface` dirs (e.g. `DiligentFX/PBR/interface`, `DiligentTools/AssetLoader/interface`). One `--start-group` on the exe, same pattern as today's `FILAMENT_LIBS`.
7. **Screenshot port is mechanical**: `ReadPixelsFromBuffer` on the swapchain color texture → RGBA/UBYTE → `stbi_write_jpg(…, 90)` → `engineStop()`; keep frame-3 one-shot and `ENGINE_RENDERDOC` (LD_PRELOAD Vulkan layer needs no code change).
8. **No git per scaffold**: the plan's "branch from main" cannot be executed by scaffold workers ("Do not use git!") — proceed in-place on the current checkout; the Filament state remains in git history regardless.

## Candidate approaches

- **A. Phase-gated incremental replacement (the plan as written)**, with two refinements: GUI stub absorbed into Phase 1, and the Phase-0 GLB probe done through a throwaway minimal program (or Radient) rather than full c-engine code. Risk: DiligentFX API learning cost in Phases 1–2 (mitigate by cribbing `DiligentSamples/SampleBase` + PBR samples). Effort: ~1–1.5 weeks, each phase gated by build + screenshot.
- **B. Big-bang rewrite of all new files, cutover at once.** Risk: integration debugging concentrated in one step; the asset-pipeline unknowns (GLB decode, KTX2 path) are only exposed at cutover; no per-phase screenshot checkpoints. Effort similar, variance much higher. Not viable for a visual-deliverable task.
- **C. Spike-only first**: standalone minimal program that loads the re-exported GLB via GLTFLoader + GLTF_PBR_Renderer with the ktx transcoder, to prove the asset path and PBR lighting before touching c-engine. Risk: throwaway scaffolding; but it isolates the two highest-unknown items. Effort: ~half day.
- **D. Hybrid A+C** — run C as the Phase-0 validation gate (the plan already mandates "verify by loading the re-exported glb in GLTFLoader/Radient"), then proceed with A. Risk: same as A; the spike budget is bounded.

## Recommended approach

**D (A with the C spike as the Phase-0 gate).** It is the plan, made explicit where the plan is thin: the Phase-1 GUI-stub requirement (lemma 3) is the single sequencing trap the plan does not call out, and the GLB re-export is a one-way door whose two-sided validation (old loader *and* new loader) costs an hour and de-risks Phases 2/3 entirely. For this to work, three things must be true: the re-exported GLB decodes in cgltf with plain-string names (verified in the spike), Diligent's TextureLoader/ktx route covers the GLB's embedded textures (Phase-0 texture-format inspection decides whether the ktx transcoder must run at load time), and the umbrella `.a` set links cleanly on both platforms with headers from the source-tree `interface` dirs (verified by the Phase-1 build).

## final (round: budget-exhausted wrap-up; task 1 — Phase 0 prep)

### GLB inspection (oghuzlands.glb, 11.6 MB, gltfpack 1.0)

- Plain JSON chunk, **no meshopt anywhere**: 0 meshopt bufferViews, `extensionsRequired = [KHR_mesh_quantization]` (from `-vn 16` normal quantization — harmless), no string compression. 100 nodes named `terrain_chunk_X_Y`, each with `extras.rigidBodyShape = MESH`; 5 bufferViews (interleaved POSITION/TEXCOORD_0/TANGENT/NORMAL + indices).
- **No embedded textures**: 0 materials, 0 textures, 0 images in the GLB. All terrain textures are external BC7 KTX2 (`models/terrain/**.ktx2`, per oghuzlands.json manifest), loaded by the game's own KTX2/BC7 path (Terrain.cpp) — Diligent's TextureLoader decodes nothing for this GLB, so the ktx transcoder question for GLB load time is: **not needed**.
- **The plan's `-kn -kv -ke` premise is wrong — they are KEEP flags, not compression** (gltfpack 1.0 `-h`: `-kn` keep named nodes, `-kv` keep source vertex attributes even if unused, `-ke` keep extras; actual compression is `-c/-cc/-cz/-cf`, none used). A/B-tested by re-running blender→terrain-chunker→gltfpack into /tmp:
  - with `-kn -kv -ke`: structurally identical to checked-in GLB (same 100 names, same extras, same per-primitive attribute sets POSITION/TEXCOORD_0/TANGENT/NORMAL, same 11,553,484-byte buffer).
  - without them: **1 anonymous node (names gone → `gltfEntitiesNamed` breaks)** and primitives reduced to NORMAL/POSITION (TEXCOORD_0 = the 0..10 UDIM UVs that drive the splat, and TANGENT, both dropped). Dropping the flags is strictly worse.
- **Conclusion: no re-export needed** — the current GLB is already loadable by Diligent's GLTFLoader (which is tinygltf-based in this version, not cgltf). The "re-export without -kn -kv -ke" step of task 1 is void; deviating from the plan on purpose, evidence above. `scripts/build-terrain.py` gltfpack call got a comment documenting this (no behavior change).

**Static libs** (linux `build-linux/`, win32 `build-win/`, identical names):
`DiligentCore/libDiligentCore.a`, `DiligentCore/Common/libDiligent-Common.a`, `DiligentCore/Primitives/libDiligent-Primitives.a`, `DiligentFX/libDiligentFX.a`, `DiligentFX/Radient/libRadient.a`, `DiligentTools/libDiligentTools.a`, `DiligentTools/AssetLoader/libDiligent-AssetLoader.a`, `DiligentTools/TextureLoader/libDiligent-TextureLoader.a`, `DiligentTools/RenderStatePackager/libDiligent-RenderStatePackagerLib.a`, `DiligentTools/RenderStateNotation/libDiligent-RenderStateNotation.a`, `DiligentTools/ThirdParty/libZLib.a` (optionally `DiligentTools/NativeApp/libDiligent-NativeAppBase.a`). **Never link `DiligentTools/Imgui/libDiligent-Imgui.a`** (bundles imgui 1.85; the game has 1.92.6). `build-linux/include/` contains only glslang — headers live in the source tree.

**Include dirs** (headers use `#include "../..."` relative paths, so adding the module `interface` dirs works; a `diligent/git` root also satisfies them):
`DiligentCore/Common/interface`, `DiligentCore/Primitives/interface`, `DiligentCore/Platforms/interface`, `DiligentCore/Graphics/GraphicsEngine/interface`, `DiligentCore/Graphics/GraphicsEngineVulkan/interface`, `DiligentCore/Graphics/GraphicsTools/interface`, `DiligentTools/AssetLoader/interface`, `DiligentTools/TextureLoader/interface`, `DiligentTools/RenderStatePackager/include`, `DiligentFX/PBR/interface`, `DiligentFX/Utilities/interface`.

**Key APIs (signatures verified in-tree):**
- Bootstrap (crib from `DiligentSamples/SampleBase/src/SampleApp.cpp`): `IEngineFactoryVk* f = LoadAndGetEngineFactoryVk(); EngineVkCreateInfo CI; CI.AdapterId = FindAdapter(...); f->CreateDeviceAndContextsVk(CI, &pDevice, ppContexts.data()); f->CreateSwapChainVk(pDevice, ppContexts[0], SwapChainDesc, *pWindow, &pSwapChain);` (SampleWindow carries the OS window — SDL3 XCB handle on Linux, see SampleApp).
- `ISwapChain`: `Present()`, `GetDesc()`, `Resize(width,height)`, `GetCurrentBackBufferRTV()`, `GetDepthBufferDSV()` (GraphicsEngine/interface/SwapChain.h).
- **Screenshot readback: `ReadPixelsFromBuffer` does NOT exist in this version** (correcting plan lemma 7). Use a `CPU_ACCESS` readback buffer + `IDeviceContext::CopyTexture(const CopyTextureAttribs&)` (GraphicsEngine/interface/DeviceContext.h:3424) then `Map` — or the swapchain DSV/RTV copy path; Tutorials/Tutorial23 shows the buffer-readback pattern.
- GLTF (tinygltf-based): `GLTF::ModelCreateInfo CI; CI.FileName = path; CI.pResourceManager = pResourceMgr; CI.ComputeBoundingBoxes = true; GLTF::Model model(pDevice, pCtx, CI);` — `model.ComputeTransforms(SceneIndex, Transforms)`, `model.ComputeBoundingBox(SceneIndex, Transforms)` → `BoundBox` (pattern in `DiligentSamples/Samples/GLTFViewer/src/GLTFViewer.cpp:153-245`); animation: `GLTFLoader::UpdateAnimation(SceneIndex, AnimationIndex, time, Transforms)` is private — drive per-frame matrices through `ComputeTransforms` (GLTFViewer anim path) and check GLTFDocument.hpp for a public animation update in Phase 2.
- PBR: `GLTF_PBR_Renderer(pDevice, pStateCache, pCtx, CI{NumRenderTargets, RTVFormats[8], DSVFormat, FrontCounterClockwise})`; `CreateResourceBindings(model, pFrameAttribsCB)`; `Render(pCtx, model, Transforms, PrevTransforms, RenderInfo{SceneIndex, ModelTransform, AlphaModes,...}, pModelBindings, pCacheBindings)` (PBR/interface/GLTF_PBR_Renderer.hpp:64/139). IBL: `PBR_Renderer::CreateInfo` flag `EnableIBL` + `SetIBLResourceViews(MaterialSRB, IrradianceCubeSRV, PrefilteredEnvMapSRV)` (GLTFViewer pattern, :394-443); per-frame data = `HLSL::PBRFrameAttribs{Camera, PrevCamera, Renderer(PBRRendererShaderParameters incl. ambient/IBL params), Lights[PBR_MAX_LIGHTS] PBRLightAttribs, ShadowMaps[...]}` (Shaders/PBR/private/RenderPBR_Structures.fxh).
- RenderStatePackager: `DiligentTools/RenderStatePackager/include/RenderStatePackager.hpp` (note: `include/`, not `interface/`); render-pass pattern in `Tutorials/Tutorial19_RenderPasses/src/Tutorial19_RenderPasses.cpp`.
- Reference apps: `DiligentSamples/Samples/GLTFViewer` (GLTF + PBR + IBL + bbox + animation, end-to-end), `SampleBase` (device/swapchain/loop), `Samples/GLFWDemo`/`ImguiDemo` (imgui backend wiring).
