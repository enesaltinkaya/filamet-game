# notes

## brainstorm

## Core difficulty

DiligentFX's SSR is a G-buffer-style post effect (needs world-space normals + roughness + depth + motion + HDR color), but the engine is a forward-lit pipeline that only produces color/motion/depth — so the whole task is (a) generating the missing normal/roughness buffer for the terrain and (b) threading SSR into the existing TAA resolve/blit path, not any CMake or library-linking work (DiligentFX is already linked and its FX context already exists for TAA).

## Reductions / key lemmas

- **The plan's component mapping is wrong: SSR is not Hydrogent.** Hydrogent is the USD renderer. DiligentFX's SSR lives in `DiligentFX/PostProcess/ScreenSpaceReflection` (`ScreenSpaceReflection` + `PostFXContext`); see `PostProcess/ScreenSpaceReflection/README.md` (integration guide) and `DiligentSamples/Tutorials/Tutorial27_PostProcessing` (CPU-side shape).
- **The integration surface is small.** `c-engine/renderer/diligent/TaaDiligent.cpp` already creates a `PostFXContext` and every frame calls `postFXContext->Execute(pa)` with `pCameraAttribsCB`, `pCurrDepthBufferSRV`/`pPrevDepthBufferSRV` (depth textures are double-buffered, `BIND_DEPTH_STENCIL | BIND_SHADER_RESOURCE`, lines ~727/1126-1128) and `pMotionVectorsSRV` — exactly the inputs SSR's `PostFXContext::Execute` needs. SSR only needs `ScreenSpaceReflection::PrepareResources/Execute` inside `taaWorldResolve`, right after that `Execute`, reusing the same context, camera CB, depth SRVs, and motion SRV. Motion vectors already follow the DiligentFX PBR NDC convention (TaaDiligent.h doc comment).
- **Shader sourcing is free.** `DiligentFXShaderSourceStreamFactory` builds a *memory* factory from `shaders_list.h` compiled into the prebuilt `libDiligentFX.a` (`Utilities/src/DiligentFXShaderSourceStreamFactory.cpp`); FX techniques create their shaders internally. No pak copy / stream-factory plumbing needed. `build-linux/DiligentFX/libDiligentFX.a` exists and is already on the link line in `c-engine/CMakeLists.txt`.
- **The color input is already the right thing.** The world renders to a linear HDR RGBA16F offscreen chain (`sceneColorTex`); SSR takes the raw current-frame color (skip `FEATURE_PREVIOUS_FRAME` for the first pass — simpler, no multi-bounce).
- **Roughness semantics:** SSR expects perceptual-roughness² by default; the engine stores perceptual roughness, so set `SSRAttribs.IsRoughnessPerceptual = true` and `RoughnessChannel` to the roughness channel.
- **One RGBA16F texture can serve both buffers** (xyz = world-space shading normal in [-1,1], a = roughness); `pNormalBufferSRV` and `pMaterialBufferSRV` both point at it.
- **Terrain-only gbuffer is a valid temporary.** SSR only spawns rays where roughness < threshold; clear the gbuffer texture to (0,0,1,1.0) (normal up, max roughness) so props/gltf pixels (absent from the buffer) don't spawn rays. Occlusion correctness comes from binding the *existing* `taaDepthDSV` read-only (depth test on, no writes) while drawing the gbuffer pass after the `props` pass. Known imperfection: rays that hit props (in depth, not in gbuffer) sample the cleared default normal — acceptable for a visual test.
- **Compositing is a one-shader change.** `GetSSRRadianceSRV()` returns (specular radiance RGB, confidence A). The final backbuffer step in `taaWorldResolve` (`blitToBackbuffer` / `casToBackbuffer`) can sample it and do `out = src.rgb + ssr.rgb * ssr.a` — debug-grade blend; no BRDF LUT / IBL split-sum needed to "see the result".
- **Matrix convention is already handled.** The existing `PostFXContext` was created with `PackMatrixRowMajor` to match the engine's runtime-gslang-HLSL convention (TaaDiligent.h/`taaFrameBegin` comments); sharing it means SSR inherits correct camera packing.
- **Depth convention:** engine is forward-Z (clear 1.0, LESS_EQUAL), what SSR assumes (reversed-Z is listed as unsupported). Caveat: ~4e4 m world scale with D32 forward-Z — raymarch hit precision may cause floating/streaks; tune `SSRAttribs` depth-buffer thickness.
- **Gate caveat:** `postFXContext->Execute` currently only runs when TAA is enabled and both depth SRVs exist (TaaDiligent.cpp `taaWorldResolve`). SSR either inherits that gate (fine if TAA stays on) or the gate must be lifted for the SSR path.
- **Project rules:** no comments in new code (AGENTS.md); shaders ship source-in-tree → pak copy via the existing CMake custom command pattern in `c-engine/CMakeLists.txt`.

## Candidate approaches

1. **Shared PostFXContext, SSR inside `taaWorldResolve`, terrain gbuffer as an extra RTV on the main terrain pass** (bind a third color RTV during the terrain draw; macro in `heightmap_terrain_ps.hlsl` outputs normal+roughness there). No extra geometry draw. Risk: changing the world pass RTV count ripples through the player/props PSOs; touches the hot path. Effort: medium.
2. **Shared PostFXContext, SSR inside `taaWorldResolve`, separate terrain gbuffer pass** (macro variant of `heightmap_terrain_ps.hlsl` early-outs after the normal/roughness chain; new pass draws terrain into an RGBA16F texture with `taaDepthDSV` bound read-only, after `props`; mirrors the existing shadow-pass pattern). Risk: one extra terrain draw per frame; macro splice must land after the full normal/roughness chain. Effort: medium, safest.
3. **Separate second `PostFXContext` for SSR.** Fully decoupled from TAA (works with TAA off). Risk: duplicated frame-index/blue-noise bookkeeping and extra GPU work; pure overhead for a temporary test. Effort: medium-plus.
4. **Custom minimal SSR from scratch.** Rejected: task explicitly wants DiligentFX SSR; its denoiser (spatial + temporal + cross-bilateral) is the hard 90%. Effort: very high.

## Recommended approach

**Approach 2**: shared `PostFXContext`, SSR executed inside `taaWorldResolve` right after `postFXContext->Execute`, plus an isolated terrain gbuffer pass writing one RGBA16F normal/roughness texture (a `GBUFFER_OUTPUT` macro variant of `heightmap_terrain_ps.hlsl`), composited by extending the final blit/cas step with the SSR radiance sample, gated behind an env var (e.g. `ENGINE_SSR=1`) so the default path is untouched. It reuses 100% of the FX infrastructure the TAA integration already proved in-tree, adds all new state in one new pass file (e.g. `SsrDiligent.cpp`), and keeps every change reversible. Must be true for it to work: (a) the terrain PS normal+roughness chain is self-contained enough to early-out after the `roughnessF` computation (~line 496) — verify the splice point; (b) `postFXContext->Execute` runs on frames where SSR should run (gate on TAA-on or lift the gate); (c) the final blit/cas PS extra sampler can be optional (1×1 clear texture fallback when SSR off) so the default output stays identical.
