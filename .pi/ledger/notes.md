## brainstorm

## Core difficulty

The crmlui C wrapper is render-agnostic by design: RmlUi compiles UI geometry and calls back into the engine (texture/geometry/scissor/viewport callbacks in `RmlParams.vulkan`), so the old engine's callback implementation is a raw-Vulkan pass (`VulkanRmluiPass`) built on old-engine helpers that don't exist here (buffer-reference descriptors, push constants, indirect draw, `vulkanCopy`/`VulkanVirtualBuf`/`VulkanPipe`). The new engine renders through Diligent, so the port is not "move a folder" — the render half must be re-implemented for Diligent, and the peripheral glue the old engine gave for free (input event stream, SDL cursors, Lua state, future tasks) has to be rebuilt from the new engine's different primitives.

## Reductions / key lemmas

1. **The crmlui contract is a small, stable C surface.** `rmlInitVulkan(RmlParams*)` + per-frame `rmlUpdate()`/`rmlRenderVulkan()` + the document/model/element API. Everything layout/CSS/event/data-model lives inside the prebuilt `librmlui*.a`. So the whole port = implement `RmlParams` correctly and call the API; RmlUi itself is never rebuilt or touched.
2. **Half the scaffolding already exists in the new engine** (verified by inspection):
   - `c-utils/datamanager/DataManager.h` already implements exactly the `dmRmlopen/dmRmclose/dmRmlread/dmRmseek/dmRmltell` callbacks the wrapper's file interface needs.
   - The engine-side rmlui assets (showFps/debug/passstats/stats documents, `milligram.css`, `global.lua`, fonts) are already in `c-engine/data/pak_0_engine/gui/` and `fonts/`.
   - The ECS `System` base is identical to the old engine's; deferred system add/remove (`ecsSystemAddDeferred`/`ecsSystemRemoveDeferred`) exists as the replacement for the old `futureTaskAdd(0, ...)`.
   - `soundPlayHover()`/`soundPlayClick()` exist (c-engine/ecs/system/sound/SoundSystem.h) — everything LuaSystem's C bindings need.
   - The frame hook slot exists: `DiligentRenderer::draw()` calls `guiDraw(context)` in the dynamic-rendering scope between the world batch and `Present`; a parallel `rmluiDraw(context)` goes in the same place.
   - `engine::renderer::diligent::{device, context, swapChain}` are exposed globally; `GuiDiligent.cpp` (ImGui) is a working in-tree template for "per-frame dynamic vertex/index buffer + pak-loaded textures + draw to backbuffer", including the `IDeviceContextVk` QueryInterface trick.
3. **`RmlVertex` maps 1:1 to HLSL.** Byte layout is `float2 position; 4-byte packed colour; float2 texcoord` = 20 bytes, 4-byte aligned — a matching HLSL struct receives the wrapper's geometry unconverted.
4. **RmlUi compiles geometry once, renders it many times** (`rmlCompileGeometry` → cached handle; `rmlRenderGeometry` per frame). So the new pass keeps a CPU-side geometry pool keyed by handle and rebuilds one dynamic vertex/index stream per frame, batched per texture. This deletes every hard part of the old pass (GPU geometry cache, virtual buffer allocator, sampled-image pool, indirect draw, per-instance textureId via buffer references) and replaces it with the same pattern ImGui uses here.
5. **Queue/draw split is mandatory and already solved by precedent.** The wrapper's callbacks fire during `ecsPostUpdate` (via `rmlUpdate()`/`rmlRenderVulkan()` from the gui manager), but drawing must happen inside Diligent's frame scope. So callbacks queue CPU-side draw commands; `rmluiDraw(context)` (renderer hook) uploads the dynamic buffers and issues draws. ImGui does exactly this split (`guiBackendFrameDiligent` in postUpdate, `guiDiligentDraw` in the renderer).
6. **Lua is mandatory, not optional.** The smallest engine document (`showFps.html`) carries `<script src="showFps.lua">`; RmlUi executes document scripts only with a wired Lua state. The old engine supplied one via a ~100-line `LuaSystem` + prebuilt `liblua.a` (both present: `cpp-thirdparty/lua/`, old `c-engine/ecs/system/lua/`), and it ports nearly verbatim. Passing `nullptr` risks a crash on the first `<script>` — treat LuaSystem as part of the baseline, not an option.
7. **Stats bindings need adaptation, not invention.** `utils::timer.{fps,elapsed,elapsedFull}` exist in the new engine; only per-pass GPU time is missing (no `renderer.rendererElapsedGpu` / `VulkanPipe` profiles in a Diligent engine) — bind 0 or frame time for the affected fields (showFps "gpu" row, DebugGui, PassStatsGui).

## Candidate approaches

**A. Diligent-native rmlui pass.** Implement all `RmlParams.vulkan` callbacks on the Diligent device/context: CPU geometry pool; per-frame dynamic vertex/index buffers (MAP, ImGui pattern); one new HLSL UI shader (position/colour/uv + ortho projection + packed colour unpack + sampler; alpha blend, depth off; shipped to the pak with the same custom-command `.hlsl` pattern the heightmap/props passes use); per-texture batched draw calls; scissor recorded per command and applied per batch via `context->SetScissorRects`. Hook `rmluiDraw(context)` beside `guiDraw`. Risk: Diligent resource lifetime — texture disposal must be deferred (`DisposeResourceDeferred`), and the dynamic-buffer double-buffering must respect the known "Diligent dynamic-buffer ring clobbering" pitfall (docs/lessons.md — read before writing this pass). Effort: moderate — one ~500-line pass + shader; every sub-pattern already exists in-tree (GuiDiligent).

**B. Raw-Vulkan side channel.** Pull `VkDevice`/`VkQueue` out of Diligent's factory (the QueryInterface trick GuiDiligent uses for imgui) and port `VulkanRmluiPass` with its old buffer-reference SPV shaders (still in the old pak). Risk: two render-state machines on one command buffer (render-pass scopes, barriers, descriptor ownership are Diligent's to manage); the old pass's helpers don't exist here so "port verbatim" is false — it's a rewrite of the old Vulkan layer plus a fragile coexistence with Diligent's. Effort: high, high-risk, architecturally against the engine.

**C. Rebuild the wrapper with its internal `RmlUi_Renderer_VK`.** The wrapper source ships a Vulkan renderer; if it were built in, the wrapper could draw by itself. Risk: rebuilding crmlui against the current RmlUi prebuilds invites version/toolchain drift, and it contradicts "I still want to use the wrapper" as the existing prebuilt artifact; the old engine demonstrably used the callback path. Effort: unknown, high-risk. Not worth pursuing.

**D. Stay on ImGui (decline the request).** Contradicts the explicit ask; listed only for completeness.

## Recommended approach

**A**, with Lua in the baseline. It is the only approach that keeps the prebuilt wrapper untouched, stays inside the engine's architecture (Diligent-only render path), and reuses patterns already proven in this exact codebase (ImGui's per-frame dynamic-buffer UI pass, the pak-shipped HLSL pattern, the `guiDraw` hook). For it to work: (a) the callback-queue / draw-hook split must hold — nothing in the callback path may touch `context` outside `rmluiDraw`; (b) the UI pass must run on the same render target inside the frame's dynamic scope, before `captureScreenshot()` so GUI shows in screenshots; (c) texture/geometry disposal must be deferred per Diligent's lifetime rules; (d) a real Lua state must be attached before the first `<script>` document loads.

### task 4 (RmlParams crash + smoke verification) — DONE, render verified

**Fixes applied:**
1. **RmlParams lifetime (the crash):** `RmlParams params{}` is now a long-lived member of `RmluiSmokeSystem` (RmluiSmoke.h), passed by pointer in added(). Confirmed the wrapper never copies it (RenderInterface_VK stores the pointer). Task 5's manager inherits this rule automatically as long as it's a system destroyed inside ecsDestroy.
3. **Render scope (the pass drew outside any render pass):** `guiDiligentDraw` (imgui) runs `context->Flush()` + its own `vkCmdBeginRendering`/`vkCmdEndRendering` and ends with `Flush()`+`InvalidateState()` — so by the time `rmluiDraw` runs, NO rendering instance is open. rmluiDraw now mirrors that: query `IDeviceContextVk`/`ITextureViewVk`, `context->Flush()`, own `vkCmdBeginRendering` (color-only, LOAD — it draws last, on top of world+imgui), draws, `vkCmdEndRendering`, `Flush()`+`InvalidateState()`. Consequences that also had to change:
   - PSO `gp.DSVFormat = TEX_FORMAT_UNKNOWN` (the color-only scope has no depth attachment; the pipeline must not expect one — depth test/write were already off).
   - `context->SetViewports` is unconditional per scope (dynamic state is per rendering instance; the conditional "only when vw != swapchain" skipped it every frame).
   - Scissor rects are clamped to the rendering area (out-of-area = UB).
4. **Descriptor-set invalidation (cmdbuf "invalid state" cascade):** this Diligent version has NO `SET_SHADER_RESOURCE_FLAG_UPDATE_AFTER_BIND` (only ALLOW_OVERWRITE) — updating the mutable texture SRV in place on a committed SRB invalidated the whole command buffer every frame. Fix: **one SRB per texture** (created in `textureAcquire`, g_UiTex set exactly once at creation; plus a `fallbackSrb`), batch draw just re-binds `t.srb`. SRBs released with the texture (deferred path + destroy).
5. **Y-flip (the "garbage" render):** the ortho must be the OLD engine's GLM y-down ortho — `_22 = -2/H`, `_42 = +1` (`glm_ortho(0, W, H, 0, ...)`), stored transposed — NOT a naive "Vulkan NDC is y-down" one (`+2/H, -1`), which renders the whole document upside-down (text at the bottom, glyphs inverted). Verified by A/B/C/D screenshot matrix (temp `ENGINE_RMLUI_ORTHO` knob, since removed): transpose+ydown (C) = upright top-left; transpose+yup (A) = upside-down bottom; no-transpose variants = off-screen/blank. `setTransform` is in fact NEVER called by this RmlUi version (transform stays identity), so the flip was purely the ortho.
6. **Data model:** the smoke system now creates the `showFps` model (rmlCreateModel + rmlBindDouble fps/elapsedCpu/elapsedCpuTotal from utils::timer, elapsedGpu → static 0.0 per lemma 7, rmlUpdateDirtyAll twice/second, rmlUnloadModel in removed) — without it the `{{ }}` bindings never resolve and the raw template text renders.
