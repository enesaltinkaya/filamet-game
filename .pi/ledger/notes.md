## brainstorm

## Core difficulty

The receive path for the filterable modes (VSM/EVSM) was never implemented on the splat terrain PS, so the fix lives in an uncommitted working tree — the real question is not "write it" but "prove it works per mode": the receive shader must decode the *DiligentFX-generated* atlas encoding (RG32 min/variance for VSM, RG32 warped moments for EVSM2, RGBA32 for EVSM4) with matching warps, biases, and the raw-vs-biased depth convention — and the only ground truth available is a headless engine, so verification must be screenshot/overlay-based rather than unit-test-based.

## Reductions / key lemmas

- **Mode enum is 1:1.** DiligentFX `BasicStructures.fxh` defines `SHADOW_MODE_PCF=1, VSM=2, EVSM2=3, EVSM4=4` (NONE implicit 0) — exactly the values the engine's `shadowMode` 0-4 passes to `ShadowMapManager::InitInfo`. No off-by-one in mode mapping; a broken mode means a broken atlas or a broken receive branch, not a misrouted mode.
- **Atlas formats are deterministic given the tree state.** With `Is32BitFilterableFmt=true` (set in `ShadowDiligent.cpp createShadowMap`): VSM→`RG32_FLOAT`, EVSM2→`RG32_FLOAT` (so `.zw` samples as 0 — the EVSM2 branch correctly skips the negative-dimension test), EVSM4→`RGBA32_FLOAT`. `bIs32BitEVSM=1` (set by the engine and re-`VERIFY`ed by DiligentFX) gates the exponent clamp at 42, matching the PS's `sTail.x > 0.5 → 42`. The generator side is therefore fixed known code; the free variables are all on the receive side and in the tuning constants.
- **Parity reduces to a binary signal.** Modes 2-4 don't need to look *identical* to PCF (VSM/EVSM are softer), but the *shadow mask* — which terrain pixels are in the caster's shadow — must match mode 1's mask at the same teleport/camera. The attenuation overlay (`ENGINE_SPLAT_SHADOW_DEBUG=2`) makes that mask explicit: pass = dark shadow region of roughly the same shape/extent as PCF's; fail = uniformly lit terrain (receive dead) or wrong-shaped/wrong-extent dark region (decoding/bias bug).
- **Decoding contract, fully written out.** Receive taps the linear SRV (not the comparison slot), reads raw moments, and tests one-tailed Chebyshev `d = lightDepth − mean; lit if d<0 else var/(var+d²)` with `var = max(moments.y − mean², floor)`, where VSM uses raw cascade z and floor `fVSMBias=1e-4`, EVSM warps both the stored moments and the receiver depth by `exp(±ex·(2d−1))` with exponents (40, 5) and a per-dimension floor `(fVSMBias·ex·warp)²`. Crucially, `fFixedDepthBias` must be *absent* in these modes (the warp/variance IS the bias; adding it double-biases → peter-panning). The tree's PS implements exactly this; the risk is constants, not structure: `fVSMBias=1e-4` is a very low variance floor (leak risk at grazing angles), and EVSM's `fEVSMNegativeExponent=5.0` vs positive 40.0 is an aggressive asymmetry that can leak under overhangs.
- **Scope boundary.** "Player shadow on the ground" means player-as-caster onto terrain — the fixed path. The glTF *player receiver* is PCF-only by design; if the user later notices the player's own body doesn't shadow in modes 2-4, that's a separate (out-of-scope) receiver, not a regression of this fix.
- No general invariant/bounding argument applies beyond the mask-parity reduction; this is an empirical verification task with a known-good generator.

## Candidate approaches

1. **Mode-sweep parity (screenshot + overlay).** Build; boot modes 0-4 via `ENGINE_SHADOW_MODE` with the same `ENGINE_TELEPORT` + `ENGINE_SPLAT_SHADOW_DEBUG=2` overlay; compare each filterable mode's shadow mask against the mode-1 baseline; then rerun mode 1 without overlay to confirm the final look. Risk: soft-vs-soft judgments are subjective — needs a pre-stated pass criterion (mask shape/extent, not luminance); a marginal leak may pass eyeball. Effort: low (one build + 5-6 launches, ~10 min).
2. **RenderDoc atlas inspection (decisive, heavier).** Capture one failing/marginal mode via `scripts/run.sh renderdoc`; `rdc.py dump` the `shadow` pass to inspect the filterable atlas output (non-trivial moments, correct per-mode layout) and the `world` pass's bound SRVs. This cleanly separates "atlas is empty/garbage (generator)" from "receive sampling wrong". Risk: toolchain cost; only needed if approach 1 flags a specific mode; the layer+preload setup is already wired but slow. Effort: medium-high.
3. **Constant-sweep A/B inside one mode.** If a mode shows leaks or acne, A/B the suspect tuning knobs: flip only `sa.fVSMBias`/`fEVSMPositiveExponent`/`fEVSMNegativeExponent` in `ShadowDiligent.cpp` and rerun. Note `fVSMBias` feeds DiligentFX's internal attrib buffer too, so a change re-tunes generator and receiver consistently — that's fine, but it must be a single coherent change, not half-tuned. Risk: over-tuning beyond "looks right vs PCF". Effort: low per iteration, only if needed.
4. **Programmatic mask comparison.** Small Python script diffing the overlay screenshots (shadowed-pixel fraction in a fixed crop around the caster) between modes; makes pass/fail non-subjective. Risk: extra tooling; JPEG artifacts; the teleport point must frame terrain + player shadow (the known recipe does). Effort: medium.

## Recommended approach

Approach 1 as the main line: one build, one sweep of modes 0-4 with the overlay, judged against the pre-stated mask-parity criterion (dark region present, same shape/extent as mode 1; no acne/noise in lit areas), followed by a final un-overlaid mode-1 shot and keeping `settings.json` at `shadowMode=1`. It's cheap, and the overlay reduces the judgment to a near-binary mask comparison. Approach 2 is the designated fallback: any mode that fails parity or looks marginal (leaks, noise) gets a RenderDoc atlas dump to bisect generator vs. receiver, and approach 3 supplies the tuning knob if the failure is bias-related. This works provided (a) the sweep uses identical teleport/camera/quality across modes so masks are comparable, and (b) any "shadow present but wrong" result is chased with the atlas dump rather than explained away.
