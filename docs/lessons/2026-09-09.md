# 2026-09-09

- `treegen` CONES-strategy default renders a conifer as a flat umbrella: the stock `configConifer` (tipConeRadius 0.22 > tipConeHeight 0.1 = flat discs, `angleSpread 0.9` splayed branches, `startFrac 0.5` so branches only fill the top half of the trunk, `coneCount 1-2`) produces a "mushroom on a stick" / parasol, not a spruce — it only reads as a conifer when (a) `coneCount >= 3` (a stacked mini-pyramid, the plan's "3-cone stack (classic)"), (b) `tipConeHeight >= tipConeRadius`, (c) `startFrac` low (~0.18) so the crown runs down the trunk, and (d) `angleSpread` upright (~0.55). Fingerprint: side-view OBJ/Blender row shows a wide flat disc (radius ≫ height) on a bare trunk; in-game the near-character trees read as acacia/umbrellas. Incident: "trees around the character look weird" — the player spawns in a conifer-only Taiga biome so every near tree was the malformed conifer; retuned `configConifer`/`configConiferFar` (near 3-cone stack / far 2-cone, 6/5 tips, trunk 0.8/0.04).
- Porting ez-tree presets to `treegen`: convert the numbers, don't transcribe them. ez-tree works in preset world units (ash_medium: trunk radius 2.0 at total height 66.4, twist 0.09/section, gnarliness per section scaled by `max(1, 1/sqrt(r_meters))`), while `treegen::generate` normalizes to unit height and applies gnarliness as `g / max(0.15, sqrt(r_unit))` per section — so the same raw value lands 2-3× stronger on thin twigs. Fingerprint of an unconverted port: stocky trunk (54% too fat), helical twist (twist is per-section in ez — 0.09×12 sections = 1.08 total), gnarled mid-branches, crown reading as a "candelabra with pom-poms" instead of the reference's slender oval. Convert: baseRadius = preset radius / preset total height (0.030), twist × section count (1.08 / -0.56), gnarliness ÷ measured divisor per level (0.005 / 0.035 / 0.028 / 0.010). Incident: "deciduous trees don't look like ez-tree default ash medium" — structure matched after conversion + cardSize measured from the reference GLB (2.67/82 ≈ 0.033) instead of assumed.
- `treegen` leaf-card budget: raising per-tip card count silently re-clips the crown when `maxTris` isn't raised — `Gen::room()` drops the last branches' cards and the build log line shows the deciduous variant at exactly `maxTris` (fingerprint: `deciduous/N=20000` after bumping cardCount; was 19384 before). Keep `maxTris` ≥ branches + tips×cards×8.
- Fast tree-shape A/B without game runs: `ENGINE_AZGAAR_PROPS_MESH_DUMP=1` drops per-variant OBJs to /tmp, and the user's reference is a GLB (`tree_LOD0.glb` = Branches+Leaves, Y-up source data) — headless Blender: `import_scene.gltf` already rotates glTF to Z-up (do NOT add another 90° X-rotation, it stretches the tree sideways), scale both meshes to unit height, render side by side; measure reference card size from the leaf mesh triangles (median longest edge ≈ size×√2 for diagonal-split quads) and crown width/height profile per decile from the vertex cloud.
- `treegen` final-level `continuation` spines are invisible tri waste: at the deepest level the radius chain (0.0225 × 0.63 × 0.76 × 0.70 ≈ 0.0056, clamped to 0.0015) is already sub-pixel at any viewing distance, but each continuation job inherits its immediate PARENT's band resolution (the near-LOD's 40 final-level spines were 12×12/8×6/6×4 = 7,296 of 28,344 tris/variant, 26 %; far LOD 1,544 of 6,688) and also carries its own leaf cards — zero silhouette effect. Rule: set `lev[levels-1-1].continuation=false` (the level whose children are the last ones) before any card/children cut; measure with the tri-counting harness A/B (`--spine`), not by eye. Incident: first waste block of the tree-rendering GPU cut (deciduous near 28,344 → 9,144; far 6,688 → 3,152).
- Leaf-card cuts: `cardCount` (per tip) is the canopy-SOLIDITY lever, `cardSize` is the AREA lever — never trade them 1:1. Dropping cards while bumping cardSize to keep per-tip area parity (count×size² ≈ const) preserves total leaf area, but the clump goes visibly more OPEN once a tip has ≤3 cards: large cards leave holes the baseline's smaller cards filled (100–200 m A/B, 250% zoom — the 3-card parity version failed, 4 cards held). Rule: to cut card tris, take the minimum card count whose A/B still reads the same clump density, at per-tip-area parity; judge on the silhouette band at range, not on 1x first pass. Incident: far-LOD cut landed at 4 @ 0.071 (area 0.0202 = parity with 6 @ 0.058) = 3,152 tris; near-LOD at 9 @ 0.070 (92 % of 30 @ 0.040 per-tip area) = 9,144 tris; a 6-card near start was rejected as too sparse even at area parity.
- TAA frame A/B is not bit-stable: establish the noise floor with an identical-geometry control pair before judging any diff. Two same-build same-scene runs differ by ~1.8 % of pixels with Δ>30 (jitter re-rolls sub-pixel positions; cf. the 2026-09-04 "600-frame screenshots are not md5-stable"). Rule: run the A/B triple (A, B, B-control) and only treat pixel-diff regions above the control's floor as real changes; heatmaps localize the change rows. Incident: validating the far-LOD cut at 100–200 m — the 1.8 % control floor is what separated the tree-band rows (real) from TAA shimmer (noise).
- RADV per-event GPU durations OVERLAP: the sum of per-pass `EventGPUDuration` replay counters (21.5–27.2 ms) exceeds the engine's own wall-frame GPU query (7.29 ms), replay-to-replay jitter is ±25 % even on bit-identical workloads (a pass with identical RasterizedPrimitives moved 21.2 %→25.4 % share), and per-draw times are not workload-monotonic. Rule: across RenderDoc captures compare PASS SHARES and same-method A/B deltas only, and use the deterministic counters (RasterizedPrimitives/SamplesPassed/submitted tris) for draw-level conclusions — never absolute ms. Incident: props-pass profile for the tree cut — the −63 % submitted / −57 % frame-rpr deltas (props share 45.4 %→40.7 %) came from those counters, while the pass-time "improvements" were only admissible as corroboration.
- Per-card lighting checkerboard on isolated leaf cards: the sun N·L term is fine (Nlight lights both faces) — the dark half of the patch comes from IBL sampling only the Nlight hemisphere, so a card turned away from the sun gets the HDRI's ground hemisphere (luminance ~0.2) against sun 3.0 + sky ~1.0 on a lit card: ~20:1 pre-tonemap per-card contrast renders the canopy as near-black clumps next to lit ones, with the pattern locked to the card geometry (static-camera visible; camera motion just moves it). Fingerprint: per-card (not per-pixel) brightness steps, IBL×4 A/B lifts the dark clumps, `ENGINE_SHADOW_NO_PROPS` changes nothing, and the reference (ez-tree) looks natural with a strong hemisphere GROUND colour doing the same job. Rule: thin tintable vegetation adds the opposite-hemisphere irradiance — `GetLambertianIBL(srf, GetIBLSamplingInfo(srf, LUT, samp, -Nlight, V), …)` into `lighting.Base.DiffuseIBL` (resolved through IBLScale/Occlusion, so `ENGINE_IBL_INTENSITY` still scales it); gate on `tintable` so baked trunks in the same draw keep single-hemisphere IBL. Canopy sRGB median 45→57, dark-pile p25 35→45, ground untouched. Side note: the runtime settings file is `build/c-game/data/settings.json` (cwd-relative) — the project-root `data/settings.json` is a decoy, so "default" A/B runs were actually TAA+SSAO-on all along.
