## 2026-09-06 — "Shimmer on distant terrain with TAA": the TAA chain was fine — the input image re-rolls sub-pixel noise per jitter phase, and (1−taaWeight) of it leaks through every frame

**Rule:** for a STATIC camera, first prove where temporal variation lives before touching the TAA pipeline: (a) two consecutive-frame screenshots with TAA OFF must be byte-identical (else the scene itself is time-varying — wind, physics, settings); (b) `ENGINE_MV_DUMP` (raw linear-quantized PNG) must show MV = 0 — do NOT judge motion from the `ENGINE_TAA_DEBUG_MV` blit screenshot, which goes through the sRGB backbuffer encode and reads as ±4 px phantom motion after naive decoding; (c) consecutive-frame diff WITH TAA on, banded by rows, localizes the shimmer (here: a full-width strip at the horizon). If (a) and (b) are clean but (c) shows a repeating flicker that is exactly reproduced one 16-frame Halton cycle later, the accumulator is working and the shimmer is (1−weight)·(per-jitter-phase input variance) — fix the INPUT or the WEIGHT, not the resolve. The dominant input variance source on far terrain: world-space procedural noise evaluated per-pixel with NO band-limiting — at tens of metres per pixel even a 48 m octave is undersampled, so each sub-pixel jitter phase draws a fresh random value (a categorical green↔straw dry-turf swap = huge amplitude). Fix: the micro-bump band's `octaveFade` (smoothstep(2,8) on the min px-per-wavelength axis, from `length(ddx/ddy(worldPos.xz))`) applied to EVERY world-anchored noise octave that feeds color (dry-turf 12/48 m, 4 m wobble, 50 m snow breakup), fading toward the field's mean contribution so the expected color is unchanged. Verified: horizon-strip consecutive diff mean 3.8–10.9 → 0.42, pixels >16/255: 14–22% → 0%. Also: the new engine's `taaWeight` settings template had regressed to 0.7 (old engine shipped 0.9) — at 0.7, 30% of the raw jittered frame leaks per pass, tripling every shimmer class; restored 0.9.

**Incident:** "shimmering on distant terrain when TAA is on, camera is static." DiligentFX TAA analysis (TAA_ComputeTemporalAccumulation.fx) showed static-camera convergence is correct (MV=0 → DepthFactor=1, MotionFactor=1, alpha→stability factor, bicubic history fetch at exact texel centers). Two red herrings burned time: (1) the `ENGINE_TAA_DEBUG_MV` sRGB misread suggested phantom motion — the raw dump disproved it; (2) two shader-fade experiments "showed no effect" because the edited .hlsl never reached the game — `cmake --build` copies shaders into `c-game/data/pak_1/materials/` but the game reads them from `build/c-game/data/pak_1.pak`, and the `data.sh` repack must be re-run after every shader edit (check `unzip -p build/c-game/data/pak_1.pak materials/X.hlsl | grep <marker>` before believing a negative result; its md5-stamp cache can also silently skip). The far-band "mottled" look the fade removes IS the aliasing (random draws from the noise field), not authored variation — ridge silhouettes, biome-tint hues and mid-ground patches survive; the far band keeps its large-scale variation through the mip/aniso-filtered grass texture and biome map.

**Wiring:** `heightmap_terrain_ps.hlsl` — turf-variation block (dry 12/48 m + wobble 4 m octaves, fade-to-mean) and the snow-line breakup (50 m, fade to mean factor 0.875); `c-utils/settings/Settings.cpp` taaWeight template 0.7 → 0.9; live `build/c-game/data/settings.json` taaWeight → 0.9. Residual (invisible) shimmer: consecutive-frame mean ~1.6–2.5 with 0 pixels >16 — texture mip-phase noise at (1−0.9) leak, converges to 0.07 within one cycle.

## 2026-09-06 — RCAS (CAS) pass: a static cbuffer set on the SRB is silently ignored (VUID-08114 every frame) — statics bind on the PSO/PRS, and `ShaderResourceVariableDesc` has no resource-type argument

**Rules:** (1) STATIC shader resource variables (cbuffers, samplers) are assigned on the PSO (`PSO->GetStaticVariableByName`) or the pipeline resource signature (`PRS->GetStaticVariableByName`, the props pass' `bindSharedStatics`) — NOT on the SRB. `SRB->GetVariableByName(stage, "cbName")` for a static returns null (the `if` just skips, no error), the descriptor stays unassigned, and every draw then fires `VUID-vkCmdDraw-None-08114` ("descriptor ... has never been updated") + the Diligent error `No resource is assigned to static shader variable 'X' in pipeline resource signature '...'` — the VUID alone looks like an update-ordering bug, the Diligent line is the fingerprint of a static never set. SRBs carry only the dynamic/mutable variables (textures that alternate per call). (2) The 3-arg `ShaderResourceVariableDesc(stage, name, varType)` constructor has NO resource-type parameter — the resource type (constant buffer vs SRV vs sampler) is inferred from the compiled shader; passing `SHADER_RESOURCE_TYPE_*` there is a compile error. (3) Per-frame cbuffer pattern for a pass with a stable buffer identity: create the IBuffer once at init, `MapHelper<T>` (MAP_WRITE, DISCARD) per frame BEFORE the SRB commit, static variable set once with `SET_SHADER_RESOURCE_FLAG_ALLOW_OVERWRITE` — the buffer identity never changes, so no SRB churn (the props' frameAttribsCB pattern). (4) A runtime-HLSL (glslang) PS reading a 4th channel of a `float3` is a hard compile error (`vector swizzle selection out of range`) — the Diligent "Failed to compile shader 'X'" + the exact line in the log points straight at it; note a shader-compile failure in this pass chain falls back to the plain blit silently, so the frame still renders — check the log for `Failed to parse shader source` before assuming the new pass ran.

**Incident:** bringing the old engine's RCAS sharpen ("cas") + its TAA-weight slider into the new engine (TaaDiligent.cpp: RCAS PS after the TAA resolve, before the sRGB blit; `casStrength` 0..1.5 in GraphicsSettings/settings.json, GUI sliders in graphics.html). First working build: `VUID-vkCmdDraw-None-08114` every frame on PSO 'taaCas' + "No resource is assigned to static shader variable 'cbCasAttribs'" — the cbuffer `Set()` had been done on the per-texture SRB (returned null, skipped); moving the `Set(casCB, ALLOW_OVERWRITE)` onto `casPSO->GetStaticVariableByName` cleared it. (Earlier build: `e.a` on the float3 center tap — glslang parse error, fixed by sampling the center as float4.)

**Verification:** `ENGINE_AUTOTEST=settings ENGINE_SETTINGS_AUTOTEST=graphics ENGINE_GRAPHICS_SETTINGS_AUTOTEST=wire` — all keys land in settings.json (`taaWeight` 0.85, `casStrength` 0.75, correct JSON types, old values untouched). `ENGINE_AUTOTEST=enter` + screenshot A/B (TAA on, `casStrength` 0 vs 1.0, frame 300): 0 VUID/CRIT both runs; B/A local-contrast ratio 1.54, mean absdiff 9.9 — the kernel is live; GPU 1.50→1.51 ms. Graphics page screenshot shows both sliders seeded from the file (85% / 100%).

## 2026-09-06 — graphics settings wiring: an rmlui decorator referencing a missing pak asset terminate()s the whole app at document load, and `!charFlag` is an int, not a bool — overloaded persist helpers silently routed every toggle into settingsSetInt's assert

**Rules:** (1) Every asset path referenced from rml CSS/HTML (decorators, `url()`, `<img>`) must exist in a pak — `utils::dataManagerRead` calls `terminate()` on a miss, so the app EXITS (quick_exit(1), CRIT line is the last log line) the moment a document referencing it loads. This reads as a mysterious hang/blank when the exit is buried in stdout; grep the log for `could not find` first. After an asset-type migration (e.g. the button.png → button.png.ktx2 rename), grep the GUI trees for the OLD extension — pak_0's milligram.css was updated but c-game's settings.css was not, which killed EVERY settings page (main menu → settings click = app exit) until today. (2) Do not overload small persistence helpers on integral types: `persist(key, !flag)` produces `bool`, and bool→int is an integral PROMOTION, which beats every conversion — so the `bool`-looking toggles bound to `settingsSetInt` and tripped its `jsonIsInt` assert (debug). In release (NDEBUG) the assert vanishes and mistyped keys get written, which trips the 2026-09-04 validation-rewrite entry: the next launch writeDefault()s away all user settings. Use distinctly-named helpers (persistBool/persistInt/persistDouble) or exact-cast every call site; note the plain `persist(key, charFlag)` form DID match a `char` overload exactly, so half the toggles worked and only some crashed — partial success is the signature.

**Incident:** wiring the graphics settings page (FSR toggle removed; controls → settings.json → rendererGraphicsApply). First headless run: the settings chain died silently — log ended at `dataManager: could not find gui/images/button.png` (the 2026-09-06 ktx2 migration missed settings.css; every settings page had been an instant exit since, the earlier same-day "settings pages work" screenshots predate it). After that fix, the wire autotest aborted with `settingsSetInt: assertion jsonIsInt failed` — gdb showed `persist("aoDisabled", 1)` hitting the int overload because `!aoEnabled` promotes bool→int, while `persist("taaEnabled", taaEnabled)` (plain char) had matched the char overload and worked. Renamed the helpers persistBool/persistInt/persistDouble.

**Verification:** ENGINE_AUTOTEST=settings + ENGINE_SETTINGS_AUTOTEST=graphics + ENGINE_GRAPHICS_SETTINGS_AUTOTEST=wire (flips 5 toggles, sets 6 slider values, closes): all 12 keys land in data/settings.json with correct JSON types; relaunch without =wire seeds every control from the file (screenshot: TAA Off, RCAS 120%, scale 130%, shadows Low, bloom/fog Off, lens 33/44/55). ENGINE_AUTOTEST=enter world run: 0 VUID/CRIT, 60 fps.

## 2026-09-06 — File-backed textures upload as BCn blocks: libktx picks SRGB block variants from the DFD (albedo → 146/BC7_SRGB, normal → 145/BC7_UNORM, verified per asset) but the RGBA32 transcode target is always UNORM (37) regardless of DFD — and utils::Image.mipSizes holds byte OFFSETS, not sizes

**Rules:** (1) The pak ktx2s are basis sources; the sampling-format decision happens inside libktx's transcode (`c-utils` `imageLoadFromData`: BC7 by channel count, BC5/BC4 for 2/1-channel DFDs) and it honors the DFD's sRGB transfer function — 768x512 logo → 146, all terrain albedos → 146, all normals → 145 (measured with a dump tool linked against the game's libktx_read). Never request `KTX_FORMAT_RGBA32` for color textures and re-derive sRGB-ness yourself: that target comes back `VK_FORMAT_R8G8B8A8_UNORM` (37) even for sRGB DFDs, and a naive "UNORM because vkFormat says 37" upload re-introduces the double-encode washout (see today's rmlui entry). `diligentCreateImageTexture` therefore takes an `srgbForUncompressed` flag that only affects plain-RGBA8 payloads. (2) `utils::Image.mipSizes` is misnamed — it stores per-level byte OFFSETS (ktxTexture_GetImageOffset results); level sizes are implicit (tight packing post-transcode, block-aligned rows: BC4 8 B/block, BC5/BC7 16 B/block). (3) Baked ktx2 mip chains upload verbatim through the helper — do NOT route them through paths that set `GenerateMips` (redundant GPU cost) and do not "upgrade" the terrain normals to BC5 without also touching the terrain PS (it reads 4-channel normals; BC5 would zero Z). (4) Props grass cards stay PNG + NEAREST minification per the 2026-09-04 RADV sRGB/LINEAR lesson; BC7_SRGB + trilinear (terrain, rmlui) inherits exactly the same sampler regime as the RGBA8_UNORM_SRGB textures it replaced — no new RADV hazard, but the lesson's constraints still apply to any new sRGB-format texture.

**Incident:** follow-up to the rmlui double-encode fix — "shouldn't we use bc7 everywhere?" turned into the compressed-upload wire-up. The prebuilt DiligentTools TextureLoader has zero basisu symbols and its KTXLoader throws "ktx2.0 is not currently supported" (KTX1 only), which is why terrain had been loading PNG decodes (mip 0 + GPU mipgen); c-utils remains the binary's one BasisU copy, so the route is c-utils decode → `diligentCreateImageTexture` block upload (DiligentRenderer.cpp).

**Fix:** `DiligentRenderer.h/.cpp` — vkFormat→TEXTURE_FORMAT map + immutable multi-mip block upload with per-level offsets/pitches and a one-line log (format/mips/KB). `HeightmapTerrainDiligent.cpp` — default-texture table switched to `.ktx2`; `RmluiDiligent.cpp` — ktx2 loads take the BC7 path, PNG/JPG stay stb → `RGBA8_UNORM_SRGB`; both retain decode-on-sample semantics. Props/cursors unchanged (PNG-only assets, raw-pixel SDL cursors).

**Verification:** `ENGINE_AUTOTEST=enter` frame-300 A/B: mean absdiff 1.12, p99 8, 0.023% of pixels >25 (BC7 rounding + wind-sway run noise). Menu logo band/edge/sky = 9/13/33 (exact old-engine values). Log shows albedos 146 + normals 145, 11 mips, 1365 KB per 1024² texture (was 5461 KB RGBA8 — exactly 4x), logo 384 KB (was 1536 KB). No VUID/validation output.

## 2026-09-06 — Main-menu logo washed out (stored 13 → displayed 62): rmlui file textures were plain RGBA8_UNORM sampled raw and written into the RGBA8_UNORM_SRGB swapchain, which encoded the already-encoded values a second time; the old engine's BC7_SRGB transcode target decoded on sample and round-tripped exactly

**Rules:** (1) The swapchain here is `TEX_FORMAT_RGBA8_UNORM_SRGB` (DiligentRenderer.cpp) — the GPU applies sRGB **encode on write**. Any shader writing already-sRGB-encoded values into it (texture sampled from a plain `*_UNORM` view, or raw RmlUi colour bytes) gets double-encoded: darks lift by encode(v) (0.051 → 0.244). (2) The parity rule for UI images is decode-on-sample: the old engine's rmlLoadTexture uploaded libktx's BC7 transcode result, and libktx honours the ktx2 DFD's sRGB transfer function by picking `VK_FORMAT_BC7_SRGB_BLOCK` (146, verified by transcoding this very logo — NOT the UNORM 145 twin) — sampler decodes, swapchain re-encodes, net identity for white-multiplied images. (3) When UI art looks washed out but its asset decodes pixel-identical to the source PNG, suspect the color-space pipeline, not the loader; verify with measured pixel pairs (screenshot vs asset) through the sRGB encode formula before touching shaders. (4) Generated UI textures (white fallback, font atlases) are space-invariant — white texels are 1.0 in both spaces and alpha is never decoded — only file-backed images need the SRGB view.

**Incident:** "first image is from old engine, second is from this engine, something wrong with logo" (2026-09-06 04:28 vs 04:56 screenshots). New-engine logo: moon scene lifted to grey, black band rendering ~#353535, with the band edge reading 62 vs the asset's 13. `utils::imageLoadKtx(…, KTX_TTF_RGBA32)` decoded pixel-identical to logo.png (absdiff max 0), so the pak asset was innocent. Measured pairs (old vs new screenshot, band/sky/edge: 9→53, 13→62, 31→101) matched sRGB-encode(raw) to within JPEG noise — double-encode confirmed. Old engine rendered the same ktx2 through BC7_SRGB + B8G8R8A8_SRGB swapchain = identity, which is why it looked correct.

**Fix:** `c-engine/gui/rmlui/RmluiDiligent.cpp` — `createRgba8` gained an `srgb` flag; `rmlPassLoadTexture` (file-backed images, both the ktx2 and stb PNG/JPG paths) creates `TEX_FORMAT_RGBA8_UNORM_SRGB` so sampling decodes to linear once. Fallback white + font atlases stay UNORM. No shader change (rmlui_ui_ps.hlsl comment updated in both the c-engine copy and the pak mirror; CMake re-copies it every build). Vertex colours deliberately stay raw — old-engine behaviour (its textured branch also skipped gamma correction; text is white so it is invisible).

**Verification:** rebuild + `ENGINE_SCREENSHOT=… ./build/c-game/c-game`: band/sky/edge pixel values return to the asset's (13/31) instead of (62/101), matching the old-engine screenshot; buttons/text unchanged.

## 2026-09-06 — "enter world" spams VUID-vkCmdBindDescriptorSets-00358/00359: the rmlui pass' zero-vertex scope-commit draw ran with the last WORLD pass' descriptor sets still stored in BindInfo.SetInfo[0] — CommitShaderResources only stores sets per binding index, the actual vkCmdBindDescriptorSets fires at DRAW time against the ACTIVE pipeline's layout, and release Diligent skips the DEV-only cross-check

**Rules:** (1) In the Diligent Vulkan backend, `CommitShaderResources(srb)` merely stores the SRB's VkDescriptorSets into `BindInfo.SetInfo[srb->BindingIndex]`; the real `vkCmdBindDescriptorSets` happens inside `PrepareForDraw` → `CommitDescriptorSets` at every draw call, pairing ALL stored sets with the pipeline layout of the currently bound PSO. `SetPipelineState` does NOT clear previously-stored sets (only DEV builds do, via DvpVerifySRBCompatibility), and all of this engine's signatures use BindingIndex 0 — so a draw made after `SetPipelineState(newPass)` but BEFORE `CommitShaderResources(newPass-srb)` rebinds the PREVIOUS pass' sets under the new pass' layout. The rebind is forced whenever the stale SRB has dynamic resources (`GetCommitMask`: `CommitMask |= DynamicSRBMask` — every pass here has a dynamic cbuffer). Signature: VUID-00358 ("layout has 3 total descriptors, but set has 8/16/18") + VUID-00359 ("requires N dynamicOffsets, but only 1 left") repeating every frame once the world draws; the descriptor count identifies the culprit pass (18 = glTF PBR cache SRB, 16 = terrain, 8 = props, 3 = rmlui itself). (2) A draw with zero vertices still executes the full PrepareForDraw machinery (and rasterizes nothing, hiding the damage) — the rmlui "commit the render scope with an empty draw" idiom MUST commit an rmlui-owned SRB first. (3) The 2026-09-05 ring-clobbering entry misfiled the two world-entry 00358/00359 pairs as "transient, one-time SRB rebuild, unrelated" — the pair count scales with how many world passes drew that frame; "transient" errors that repeat after a state change (tiles uploaded, props resident) are a per-frame binding-order bug, not a one-time rebuild.

**Incident:** "when i click enter world, i see some vulkan errors". `ENGINE_AUTOTEST=enter` showed the first pair (18-desc/4-dyn glTF set) two frames after ENTER WORLD (only gltf had drawn; terrain tiles were still uploading), then 16-desc (terrain) sets right after the first tile uploads, then 8-desc (props) sets every frame in steady state — exactly the frame order worldDraw → terrain → props → rmlui. `RmluiDiligent.cpp`'s zero-vertex draw sat between `SetPipelineState(rmluiPipeline)` and the first per-batch SRB commit, with nothing rmlui-owned in SetInfo[0].

**Fix:** `c-engine/gui/rmlui/RmluiDiligent.cpp` — commit `fallbackSrb` (an rmlui SRB, the fallback-white-texture binding) immediately after `SetPipelineState(pipeline)` and before the zero-vertex draw; the per-batch loop then overwrites SetInfo[0] with the per-texture SRBs as before.

**Verification:** `ENGINE_AUTOTEST=enter ENGINE_LOG_TIMEOUT=60000 ENGINE_SCREENSHOT=… ENGINE_SCREENSHOT_FRAME=300` + radeon ICD: 0 VUID/validation lines in the whole run (pre-fix: 10+ reports hitting the duplicate_message_limit per session); frame-300 screenshot identical to before (terrain, props, character, all four rmlui guis) — the empty draw rasterizes nothing, so there is no visual delta by construction.

## 2026-09-06 — Prop grass rendered half in near-black shadow: the ported `Nlight` (unflipped normal for thin double-sided vegetation) was computed in the props PS but never used — the flipped back-face normal went to the sun and the IBL, so NdotL == 0 on every face turned away from the sun

**Rule:** when porting a lighting rule, check that every intermediate feeds the light — a variable that is computed and never referenced is a dropped rule, not a refactor. Specifically: this engine's props pass renders double-sided (CULL_MODE_NONE) and flips the normal on back faces (`N = FrontFacing ? N0 : -N0`) so closed solids keep slab undersides unsunlit; but thin vegetation (flag bit 1: grass tufts/cards, reeds, palms, flowers) must light BOTH faces with the UNFLIPPED stored normal — a blade's back face faces the sky like its front. The flipped back-face normal has NdotL == 0 (direct sun) AND samples the irradiance cube's ground hemisphere (IBL), so half of every tuft renders near-black, exactly the defect the old engine's `azgaar_props.frag` documents avoiding (`Nlight` for sun, species 0/6/9/12).

**Incident:** "lighting doesnt look right on these prop grass". `props_ps.hlsl` (DiligentFX PBR port) declared `float3 Nlight = (In.Flags & 2u) != 0u ? N0 : N;` — faithful to the old engine — then lit with `base.Normal = N` anyway; `Nlight` was dead code. The `propsground` camera looks toward the sun (+X+Z, sun dir (0.6, 1, 0.5)-ish), so the frame is dominated by grass back faces: before the fix the foreground reeds were half black / half bright green, and the defect is view-dependent (front-face views looked fine — "not always").

**Fix:** `c-engine/renderer/diligent/shaders/props_ps.hlsl` (canonical source; CMake copies it into `c-game/data/pak_1/materials/` every build — edit the mirror, not the pak copy) — `base.Normal = Nlight; base.NdotV = dot_sat(Nlight, V);`. Both sun (`ApplyPunctualLight`) and `ApplyIBL` now run on the lighting normal; closed solids are untouched (their bit-1 is clear, so `Nlight == N`).

**Verification:** A/B headless (`ENGINE_AUTOTEST=enter` + `ENGINE_SCREENSHOT` + `ENGINE_SCREENSHOT_FRAME=900` — without AUTOTEST the shot is just the main menu; the world loads on ENTER WORLD): `propsground` (looking into the sun, back faces dominant) before shows black half-blades on the foreground reeds and scattered dark tufts, after shows every blade lit on both sides, uniform green; `props` (oblique, front faces) is a stable control. Trees (closed solids) unchanged in both.

## 2026-09-06 — KTX-Software relinked after the filament removal: c-utils Image decodes ktx2 again (old engine verbatim), cursors back on .png.ktx2

**Rule:** the 2026-09-04 one-BasisU rule stands unchanged — never two BasisU
transcoders in one binary. With filament gone, the ONLY BasisU in the binary
is KTX-Software's vendored one inside `libktx_read.a`; the prebuilt Diligent
libs define zero basisu/basist symbols (nm scan over all `libDiligent*.a`,
2026-09-06), so the collision this file's 2026-09-04 entry describes cannot
recur unless a second copy is added. If you ever see "ktx2 transcode failed"
again: grep the link line for a second basisu before anything else.

**State:** the 2026-09-04 fix ("c-utils keeps only stb decode;
`imageLoadKtx` is a stub") is obsolete. `c-utils/image/Image.cpp` restored
the old engine's `imageLoadFromData` ktx2 branch and `imageLoadKtx` verbatim
(ktxTexture2_CreateFromMemory → transcode-if-needed → mip offsets →
memcpy), and `c-game/CMakeLists.txt` links
`${thirdparty}/ktx/git/${platform_dir}/libktx_read.a` — the single lib the
old engine used (its basisu objects are pulled lazily: uncompressed ktx2
never drags the transcoder in, ETC1S/UASTC loads do; both resolve inside the
archive). Cursors load `images/cursor{Arrow,Hand}.png.ktx2` (uncompressed
RGBA32) via `imageLoadKtx(path, KTX_FORMAT_RGBA32)` exactly like the old
engine's `SDLWindowSystem::loadCursor`, keeping this engine's nullptr →
system-cursor fallback. Terrain default textures stay PNG by choice

`imageLoadKtx(path, KTX_FORMAT_RGBA32)` (GUI uploads are RGBA8-only, so

displays. Callers of plain `imageLoad` that read raw RGBA pixels (Azgaar
grass-card scans) must stay on PNG paths.
